什么是 MVCC

Multi-Version Concurrency Control，多版本并发控制

它允许多个事务同时读取和写入数据，而不会相互阻塞

为什么需要 MVCC

先来说一下表的读写操作

当对表中的某一行数据，先进行写操作，紧接着又来了读操作，那么就要等写操作完后，才能开始读操作。这就是所谓的读写冲突

在并发比较高的场景下，性能就会比较低下。而 MVCC 就是要解决这个问题，让读写不再冲突，使其性能可以高效起来

例子引入

表结构：person

现在有 4 个事务：101 - 104

这 4 个事务，同时开始执行，执行的顺序都是从上到下，分析其具体的执行过程：

  1. 首先是事务 102，找到 ID 为 1 的这行数据，将 name 修改为 axing2，修改完后直接提交
  2. 接着是事务 103，找到 ID 为 1 的这行数据，将 name 修改为 axing3，修改完后直接提交
  3. 接着是事务 104，执行第一次查询：查询 ID 为 1 的这行数据
  4. …

（要注意：虽然事务 101 已经开启了事务，但它的修改操作，是在事务 104 第一次查询之后的）

undo log

到这里 undo log 就要上场了

因为事务 104 在第一次查询时，事务 102 和 103 已经执行了修改操作

undo log 会在每次更新时，将该行数据的旧版本保存下来，以节点的形式进行存放，保留其历史版本，直到确认没有事务再需要它为止

因为事务 102 先于 103 执行修改，所以 103 的操作是最新的，那么 103 就要在 102 的上面

因为 undo log 是按照从新到旧的顺序来排列的，执行就是从上到下的顺序了

节点之间用回滚指针来进行连接，除了这两个节点，还有一个是执行事务前初始记录的节点，初始的内容是 axing，同样也要关联起来

ReadView

还有个重要的东西叫 ReadView

这个东西是在当前读取的时候产生的一个视图，可以理解为像拍照一样，把这一瞬间的画面给拍下来，保存到照片中

对应在事务中，就是进行快照读的时候，在这一瞬间产生的数据给保存下来，这样其他事务在修改数据时，就不会影响到这个快照视图了

快照读：读取某一时刻的快照，就是指常规的 select * from ... where ...

当前读：读取当前时刻最新的值，需要在对应的数据上加锁，形如 select * from ... where ... for update

4 个属性

ReadView 中，还有重要的 4 个属性：

属性 含义 等于什么
m_ids 活跃中的事务 ID 列表 一个集合
min_trx_id 活跃中的最小事务 ID min(m_ids)
max_trx_id 分配给下一个事务的 ID 已分配的最大事务 ID + 1
creator_trx_id 生成 ReadView 时所在的事务 ID 当前事务 ID

判断条件

针对这 4 个属性，有相对应的判断条件：

trx_id：要判断的事务 ID

条件 说明是什么 是否能访问
trx_id = creator_trx_id 当前的事务 是
trx_id < min_trx_id 已提交的事务 是
trx_id > max_trx_id 当前事务后开启的事务 否
trx_id in m_ids 未提交的事务 否
trx_id not in m_ids 已提交的事务 是

按照这些判断条件，划分出五个区域来：

首先，满足第一个判断条件的话，就是当前的事务

接着，有两个边界：

  • min_trx_id：小于此边界的，就是已提交的事务
  • max_trx_id：大于此边界的，就是当前事务后新开启的事务

然后，在这两个边界中，又分为：

  • 在 m_ids 中：就是未提交的事务
  • 不在 m_ids 中：就是已提交的事务

结论：

  • 可以访问：已提交的事务，当前的事务
  • 不能访问：未提交的事务，当前事务后新开启的事务

第一次查询分析

接着分析之前的例子

和这 4 个属性，以及判断条件结合起来

以事务 104 的第一次查询，作为开始，来对应下面的 4 个属性

trx_id = 103

属性 含义 值
m_ids 活跃中的事务 ID 列表 101，104
min_trx_id 活跃中的最小事务 ID 101
max_trx_id 分配给下一个事务的 ID 105
creator_trx_id 生成 ReadView 时所在的事务 ID 104

依次看判断条件，最终落在 trx_id not in m_ids，所以是可以访问的，能看到的就是事务 103 的值，查询的结果是 axing3

第二次查询分析

接着就是要分析第二次查询，而这第二次查询，要分为不同的隔离级别来看：读已提交和可重复读

MVCC 是在读已提交和可重复读的隔离级别下生效的

读已提交

首先看读已提交

当第二次查询时，会重新生成 ReadView，而事务 101 已经提交了，就要看重新生成的 ReadView 变成了什么样

trx_id = 101

属性 含义 值
m_ids 活跃中的事务 ID 列表 104
min_trx_id 活跃中的最小事务 ID 104
max_trx_id 分配给下一个事务的 ID 105
creator_trx_id 生成 ReadView 时所在的事务 ID 104

依次看判断条件，最终落在 trx_id < min_trx_id，所以是可以访问的，能看到的就是事务 101 的值，查询的结果是 axing1

可重复读

再看看可重复读

其实，可重复读的关键，就是第二次查询时，不会再重新生成 ReadView，而是用的第一次查询的 ReadView

trx_id = 101

属性 含义 值
m_ids 活跃中的事务 ID 列表 101，104
min_trx_id 活跃中的最小事务 ID 101
max_trx_id 分配给下一个事务的 ID 105
creator_trx_id 生成 ReadView 时所在的事务 ID 104

依次看判断条件，最终落在 trx_id in m_ids，那就是不可以访问的，所以事务 101 节点，对当前事务不可见

接着就是下一个节点 trx_id = 103

也是一样，依次看判断条件，最终落在 trx_id not in m_ids，所以是可以访问的，能看到的就是事务 103 的值，查询的结果是 axing3

所以，在可重复读的隔离级别下，两次查询的结果都是相同的，都是 axing3

事实上，即使事务 101 在第二次查询前已提交，在可重复读隔离级别下，事务 104 仍看不到它，因为 ReadView 在事务开始时就固定了

总结

MVCC 的核心思想是用空间换时间——为数据行维护多个版本，每个事务看到的是它开始时数据库的一个快照，而不是实时的最新数据

这使得 MySQL 在高并发读写场景下，仍能保持良好性能
